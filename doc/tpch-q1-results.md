## 7. 分析

### 7.1 Backend 交叉点

- **SF<=0.03**：Flying Start 最优。数据量小，FS 编译+执行总时间 < LLVM 纯编译时间。
- **SF=0.1**：交叉点附近。Adaptive (12.08ms) 首次略优于 FS (12.16ms)，但差距 <1%。
- **SF>=0.3**：Adaptive 明确最优。LLVM 编译来得及切换，Adaptive (17.04ms) 优于 FS (35.06ms) 和 LLVM (22.29ms)。

### 7.2 Adaptive 效果

Adaptive 在所有 SF 下都接近或达到最优：
- 小数据（SF<=0.1）：纯 FS 执行，无 LLVM 编译开销，性能接近纯 FS（额外 ~0.5ms adaptive 调度开销）。
- 大数据（SF>=0.3）：FS 先跑 ~63 个 morsel，LLVM 编译完成后切换，总时间优于纯 LLVM。
- SF=10 时 Adaptive (229.5ms) vs LLVM (241.7ms)，Adaptive 快 5%，因为 FS 在 LLVM 编译期间已处理了 64 个 morsel。

### 7.3 Compile vs Execute 占比

| SF | FS compile % | LLVM compile % |
|---:|-------------:|---------------:|
| 0.01 | 8.2% | 96.5% |
| 0.1 | 1.2% | 86.5% |
| 1 | 0.1% | 43.4% |
| 10 | 0.01% | 7.5% |

FS 编译开销始终可忽略。LLVM 在小数据几乎全花在编译上，SF>=10 时编译占比降至 7.5%。

### 7.4 关键发现

1. **FS ns/row 恒定 ~19-20ns**：与数据量无关，代码质量稳定。
2. **LLVM ns/row 略微上升**：SF=0.01 时 3.3ns → SF=10 时 3.7ns，大数据集 L3 cache miss 有微小影响。
3. **Adaptive switch point 稳定在 morsel 60-65**：反映 LLVM 编译时间（~16ms）的稳定性。
4. **vs DuckDB 优势随 SF 增大**：1.3x → 6.2x，JIT 执行吞吐远超 DuckDB 解释执行。
